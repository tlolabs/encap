# Core runtime release integration

This branch prepares a new application release; existing release tags and published bytes are untouched. AVID Core owns FFmpeg 9.0.1 Recipe 7 and both tools come from build `25d19098a22936638b0e2a70616083d929fe409c`, run `36681249099`. All six targets are pinned in `runtime/core-runtime.json`. Both applications vendor the identical shared `script/core_runtime.py`; its digest is checked by runtime ownership tests. `runtime/core-candidate.json` is a distinct explicit unpublished qualification source.

Production acquisition is deliberately blocked until the qualified Core runtime is published and its exact release revision and authenticated manifest digest are pinned. Native host qualification uses manual workflow dispatch with `qualify_core_candidate=true`. Candidates cannot enter tag, push or PR publication paths. Original Core metadata stays unchanged when platform signing modifies executable bytes; `signed-payload.json` records original and derivative hashes and the signing transformation.

Distribution formats are macOS ZIP, Windows portable ZIP and Linux AppImage. Old installer/deb/tar/DMG publication machinery is not a release prerequisite. The Windows Azure workflow builds/tests natively first, signs on the supported Windows x64 runner, then verifies the final signed ZIP on its actual native architecture. Required configuration is: secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`; variables `AZURE_SIGNING_ENDPOINT`, `AZURE_SIGNING_ACCOUNT`, `AZURE_CERTIFICATE_PROFILE`, `AZURE_SIGNING_SUBJECT`. Configure workload identity credentials scoped to this repository/ref and the Artifact Signing Certificate Profile Signer role. The owner confirms no Azure signing account exists, so no Windows production package can be claimed signed.

Linux requires Actions secrets `LINUX_GPG_PRIVATE_KEY_B64`, `LINUX_GPG_PASSPHRASE` and public variables `LINUX_GPG_PUBLIC_KEY_B64`, `LINUX_GPG_FINGERPRINT`. The approved maintainer fingerprint is `F7E74ED98DB485D03F2565B96B68B73FE752FD16`. Run `python3 script/configure_linux_signing.py` in a secure interactive terminal to make the specifically approved transfer to ATIV/EnCAP. Signing verifies the detached signature against the same identity, and published AppImages also require GitHub/Sigstore attestations.

Local macOS Developer ID identity is usable: Thomas Lothian, Team ID VR64M92P2M. Keychain notary profile `EnCAP` authenticates successfully. This does not configure CI Apple secrets. Local final signing/notarization is supported without exporting that private key. A newly packaged app must be submitted, accepted, stapled, re-ZIPped and validated after extraction; previous 2.0.4/0.2.4 notarization is historical mechanism evidence only.

Native smoke/media/lifecycle evidence is distinct from manual UI/accessibility and actual authenticated version upgrades. None of those manual or real-upgrade entries is considered passed by editing the ledger or signing metadata. No application release may depend on an unpublished Core candidate.

Application publication is implemented in `application-release.yml` and `script/application_release.py`. `runtime/application-qualification.json` records the full matrix with all unperformed checks still awaiting evidence. ATIV retains per-target publication and EnCAP requires all six targets. Publication rejects candidates, mismatched Core identities, altered artifacts, unperformed signing/upgrades/manual acceptance, unsafe packages and existing release identities. Final update metadata is signed using the deployed existing key; verified downloads and attestations precede publication. The original app build commit is distinct from the later evidence/promotion commit.
